# 六场景最佳实践速查

> 这是全项目最实用的一页。给定约束，直接查表。

## 一页速查

|---|---|---|---|---|---|
| 1 | 课程项目 / 快速原型 | >90%，1–3 天 | CPU-only | `tinyfast_xxs` | 91%+ / 300–450 img/s |

## 场景一：课程项目与快速原型验证

**约束**：需要精度 >90%，时间预算 1–3 天，无需极致吞吐。

**路径**：CPU-only ONNX。

**步骤**：

1. 从 `tinyfast_xxs` 系列出发（91.09%，375 img/s）
2. 使用 teacher ensemble 软标签 + blend 蒸馏训练，可稳定达到 91%+
3. 导出 ONNX 后使用 `quantize_static`（INT8, QOperator）
4. 板端使用 `intra=2, inter=1, batch=256`
5. 整体部署时间约 **0.5–1 天**

**预期**：精度 91%+，吞吐 300–450 img/s，完整 10000 张测试约 25–35 s。

---

## 场景二：精度优先、吞吐宽松

**约束**：尽量高的分类精度（如医疗辅助分诊、高价值商品识别），现场离线推理，可接受
较低吞吐（>100 img/s 即可）。

**路径**：CPU-only ONNX，精度优先档。

**步骤**：

1. 使用 `tinyplus_kd_v1_fulltrain`（92.21%）
2. **Full-train**：在全部 60000 张训练图上定型
3. 保持 EMA checkpoint
4. 板端目标吞吐约 186 img/s，完整 10000 张约 53 s

**进一步提升**：若需要超过 92.5%，可考虑增大隐藏层宽度（但需重新测试吞吐是否仍可
接受），或尝试 label smoothing + cutout 增强。

⚠️ 注意：本项目里"增大宽度"的收益是递减的 —— 从 `tinyfast_xxxs` 到 `tinyplus`，
参数量涨 4.9 倍，精度只涨 1.76 个点，吞吐跌到 42%。

---

## 场景三：高吞吐批量推理（生产线视觉检测）

**约束**：高速批量分类（如工厂传送带服装自动分选），吞吐第一，精度可接受轻微降低
（>83%）。

**路径**：BNN-PYNQ PL 侧 FPGA 路线。

**步骤**：

1. 使用 `paper_bnnpynq_lfc_fashion_1w1a` 部署链（已验证）
2. 板端 batch=256 下吞吐约 **154 096 img/s**（较 CPU 路线高约 350×）
3. 若需提升精度，参考场景六的蒸馏提升策略
4. **注意板端 bitstream 下载时间（约 1–2 s），应在系统启动时一次性完成**

⚠️ **注意事项**：BNN 路线当前精度 83.16%，**Shirt / Pullover / Coat 类混淆率较高**。
若应用场景中这些类别误分类代价高，需充分评估可接受性 —— 平均数会掩盖分层风险。

---

## 场景四：精度与吞吐双约束（智能零售货架管理）

**约束**：同时满足精度 >90% 与吞吐 >200 img/s（如实时货架监控）。

**路径**：CPU-only 中间档，配合流水化批处理。

**步骤**：

1. 使用 `tinyfast_xxs`（91.09%，375 img/s）
2. 将图像缓冲至 batch=256 后批量送入推理（**系统设计需支持图像缓冲队列**）
3. 推理结果异步返回，避免阻塞图像采集流
4. 整体系统延迟约 0.7 s（batch 积累 + 推理时间）

**如需降低延迟**：减小 batch_size 至 64，吞吐约降至 200–250 img/s，单张延迟可降至
约 5 ms。

这是唯一一个"精度档"和"速度档"都不满足、必须取中间值的场景 —— 也是现实中最常见的
一种。

---

## 场景五：开发迭代期（多模型快速对比）

**约束**：需要频繁更新模型（持续学习、A/B 测试），模型可能数小时内多次更新，不适合
长周期 FPGA 重综合。

**路径**：CPU-only ONNX，利用蒸馏快速复制机制。

**步骤**：

1. 一次性建立高质量教师 + 离线 soft target
   （`teacher_targets_full_train.npz`）
2. 每次架构迭代只需重新运行学生训练（约 **10–30 分钟**）
3. 导出 ONNX + INT8 量化，无需重新综合 bitstream
4. 通过 SCP/SFTP 将新 ONNX 推送到板端，直接替换（无需重启 PYNQ 服务）
5. 更新周期约 **15–40 分钟/次**，远小于 FPGA 重综合的 2–8 小时

**这条场景最能体现"一次建立教师体系、多路复用软标签"的价值。** 教师的成本被摊销到
无限次迭代上。

---

## 场景六：面向未来的高质量 FPGA 主线

**约束**：长期目标是在 PYNQ-Z1 上实现精度 >93%、同时利用 PL 侧数据流加速获得远高于
CPU 的吞吐，接受 1–2 周工程投入。

**路径**：高质量 FINN-friendly 主线，从本项目工程基础继续推进。

**路线图**：

1. **解决 BRAM fit 问题**：热点在 `memstream_axi_wrapper`，可尝试调整 `ram_style`
   （LUTRAM vs BRAM）或减少 weight streaming 并发度
2. **解决 stitched-IP 正确性问题**：在受信任 Linux 环境下重跑 stitched rtlsim，
   排除 Windows 工具链残留影响
3. **出发点**：`finnconv_direct_head8_kd_noncheat`（已完成
   estimate / codegen / ipgen / OOC synthesis）
4. **预期吞吐**：若 FINN 数据流化完全正确，4W4A 模型理论吞吐可达
   **1000–10000 img/s** 量级，远超 CPU 路线

现状与卡点见 [05 - FPGA 部署](./05-fpga-finn-deployment.md)。

```
开始
 │
 ├─ 需要精度 > 90%？
 │   ├─ 否，且吞吐是唯一约束 ──────────────→ 场景三（BNN，83.16% / 154k img/s）
 │   └─ 是
 │       ├─ 吞吐也要 > 200 img/s？ ────────→ 场景四（tinyfast_xxs，91.09% / 376）
 │       ├─ 精度要 > 92%，吞吐可放宽 ──────→ 场景二（tinyplus_kd，92.21% / 187）
 │       └─ 都没有强约束 / 要快 ───────────→ 场景一（tinyfast_xxs，0.5–1 天）
 │
 ├─ 模型要频繁更换？ ──────────────────────→ 场景五（软标签复用，15–40 min/次）
 │
 └─ 有 1–2 周，追求精度与吞吐双优？ ───────→ 场景六（FINN 主线，理论 1k–10k img/s）
```
