# 平台与路径选择

## PYNQ-Z1 资源

| 资源 | 规格 |
|---|---|
| SoC | Xilinx Zynq-7020 |
| PS | 双核 ARM Cortex-A9 @ 650 MHz |
| PL | Artix-7 XC7Z020 |
| LUT | 53 200 |
| FF | 106 400 |
| BRAM (36K) | 140（等效 RAMB36，工具侧按 280 块 RAMB18/36 计） |
| DSP | 220 |
| 片上 SRAM (PS) | 256 KB |
| DDR3 | 512 MB |
| OS | PYNQ Linux 3.0（Ubuntu） |
| Python | 3.10（PYNQ venv） |
| ONNX Runtime | 1.16.0 |

BRAM 是这条路上最紧的资源。后面所有的资源收敛努力，本质上都是在跟 280 这个数字
较劲。

## 两条路径

### PS 侧（CPU）

直接在 Cortex-A9 上跑，不需要碰 FPGA 工具链。

**优势**：部署极简、对模型结构无约束、可享受 ONNX Runtime 的算子融合与静态量化、
模型更新不需要重新综合。

**劣势**：双核 A9 算力有限，模型一大吞吐就断崖式下跌；用不上 PL 的并行资源。

### PL 侧（FPGA Fabric）

把网络映射成定制数据流加速器。

**优势**：超低延迟高吞吐（量化网络可完全流水化）、每次推理能耗比 CPU 低一个量级、
对 BNN 的 XNOR-popcount 天然友好。

**劣势**：工具链复杂开发周期长、模型结构必须满足算子约束、资源有限存在 fit 失败
风险、Windows 原生 FINN 需要额外工程修复。

## 决策框架

| 决策维度 | PS (CPU-ONNX) | PL (FINN/BNN) |
|---|---|---|
| 部署周期 | 短（天级） | 长（周级） |
| 模型结构约束 | 几乎无 | 严格（FINN-friendly） |
| 精度上限（本项目） | 92.21% | 83.16% (BNN) / 93.55%（主线待完成） |
| 吞吐（实测） | 445 img/s | ~154 096 img/s（BNN, batch=256） |
| 功耗 | 相对较高 | 相对极低 |
| 调试难度 | 低 | 高 |
| 适合场景 | 快速原型 / 精度优先 | 高吞吐 / 低功耗 |

## 两条路不互斥

这是实践中一个反直觉的发现：**PS 和 PL 的验证互相促进。**

- PS 侧 ONNX 路线先证明了端到端数据流（预处理 → 推理 → 输出）完整可行，为 PL 侧
  调试提供了参照 golden；
- PL 侧建立的硬件语义验证方法，反过来加深了对模型量化行为的理解。

如果只能先做一条，先做 PS。它更快给出 golden，而这个 golden 是后面所有 PL 调试
的锚点。

## 一个被忽略的选型变量：runtime 可用性

路径选择不只看"PS 还是 PL"，还要看**目标板上到底装得上什么运行时**。

PYNQ-Z1 是 `armv7l` 架构，官方 PyPI 的 onnxruntime wheel 并不总能装上。这直接
决定了是走 ONNX Runtime（本项目实测 445 img/s 量级）还是退回板端预装的 OpenCV DNN
（量级低得多）。

这个变量有个让人不舒服的性质：**它带来的性能差距可能比多数"模型优化"的收益还大，
而且完全不由模型决定。** 选型前先 `pip install onnxruntime` 试一下，比调三天模型
结构有用。
