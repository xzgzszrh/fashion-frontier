# 负结果与教训

> 这部分记录的是**没做成的事**和它们的原因。
> 一个只写成功的项目，读者学到的是"这样做能成"；写上失败，读者才能学到"那样做会
> 浪费三天"。

## 失败案例清单

| # | 案例 | 表象 | 真实原因 | 代价 |
|---|---|---|---|---|
| 1 | EfficientNet-B0 直接上 ARM CPU | ~10 img/s | 未把部署硬件纳入设计空间 | 一次完整重设计 |
| 2 | `q_md` 系列进 FINN | estimate 拒绝 | 含 GlobalAveragePool 等算子 | 结构重做为 head8 |
| 3 | `q_l` 系列 | 未进入 build | 权重存储 ~870 KiB 超 BRAM | 0（粗估提前排除） |
| 4 | FINNConv Head8 板端 | 主机 93.55% / 板端 5% | stitched-IP 集成路径问题 | 主线未闭环 |
| 5 | KD-BNN 1W1A | ~10% 精度 | 一次改太多变量 | 一次重做 |
| 6 | 二值 LFC 蒸馏 | 崩到随机 | KL 与 sign 激活冲突 | 一次重做 |
| 7 | EB0 精修/续跑 | val 涨 test 跌 | 单模型边际递减 | 时间 |
| 8 | 全量训练 | 94.63% < 94.77% | 失去验证集监控 | 时间 |

案例 3 是唯一一个"代价为零"的失败 —— 而且是唯一一个**提前做粗估**的。这不是巧合。

## 教训一：部署约束前置

> 在资源受限平台上，模型设计必须从一开始就服从部署约束，而不能先训练后适配。

三次结构性重做都源于违反这一条。正确做法是在设计的第一步就把以下约束纳入设计空间：

1. FINN 支持的算子集
2. BRAM / LUT / DSP 资源预算
3. 目标吞吐下的延迟约束
4. 可量化性与可导出性

## 教训二：分层验证是硬件调试的基本原则

从训练逻辑、ONNX 导出、cppsim 到 stitched rtlsim 再到板端执行，**任何层次的问题都
必须被定位到正确的层次**，不能依靠单一实验结论跨层得出结论。

完整表格见 [05 - FPGA 部署](./05-fpga-finn-deployment.md#64-分层验证把问题定位到正确的层-)。

补充一条经验：**如果一个"应该更快"的部署路径反而更慢了，先怀疑链路，不要怀疑
模型。** 数量级上的反常（比 CPU 慢几百倍）几乎从来没有模型层面的解释。

## 教训三：一次只改一个变量

KD-BNN 崩到 10% 的根因不是"蒸馏对二值网络无效"，而是**同时改了三个高风险变量**：

- 二值 LFC 结构
- KL 蒸馏损失
- cross-entropy 与 sign 激活的兼容性

三个一起上，崩了以后无法归因。正确顺序是：先跑通纯净基线（83%），**确认它成立**，
再单独加蒸馏。

> 对于极端量化模型（1W1A），应优先稳定纯净训练过程，再逐步引入蒸馏。

## 教训四：工具链 bug 极易被误认为模型设计错误

Windows 原生 FINN 路线上修的 bug：

- `create_stitched_ip.py`：stitched-IP 实例名过长
- `templates.py`：Vitis HLS 2022.2 include 路径规范化
- `replace_verilog_relpaths.py`：`$readmemh` 反斜杠路径错误
- 工具发现逻辑：适配 AMD Unified 2025.2 的 `vitis-run --mode hls`

路径格式、实例命名、反斜杠转义 —— **这些问题的表象和"模型结构设计错了"几乎一样。**

> 强烈建议将 host/tool 问题与 design 问题明确分离：任何"神秘"的构建或仿真失败，
> 都应先排查工具链层面。

## 教训五：上界参考线必须与正式结果隔离

Ensemble 精度（94.88%）不是可部署结果，它是蒸馏的知识源。把它和单模型结果混在一张
表里，会让人误以为可部署精度是 94.88%。

**`benchmarks/results.csv` 里 `deliverable` 这一列就是为此存在的。**

## 教训六：只交付一个模型是危险的

边缘推理应用的需求**通常在项目过程中持续演化**，事先无法确定最终用户需要"最高
精度"还是"最快速度"。

维护多档交付体系后，无论偏好如何变化，都可以在现有候选上直接选择，无需重新训练。

## 教训七：验证集不是"浪费掉的 10% 数据"

全量训练（val_split=0）得到 94.63%，**低于**保留验证集的 94.77%。直觉上"数据更多
应该更好"，但失去监控后早停点变差，两相抵消。

同理：EB0 精修后 val +0.22% 而 test −0.22% —— **不要只看 val 选 checkpoint。**

## 教训八：粗估先于构建

FINN full build 要几小时。用权重存储粗估筛候选，几分钟就能排掉注定装不下的模型。

```
q_l: ~870.2 KiB → 超出 PYNQ-Z1 可接受范围 → 排除，一次 build 都没浪费
```

**在任何"单次尝试成本很高"的流程前面，都值得加一个廉价的预筛。**

## 教训九：目标板的 runtime 可用性是独立的选型变量

PYNQ-Z1 是 `armv7l`，官方 onnxruntime wheel 并不总能装上。能否用上 ONNX Runtime，
与模型无关，但带来的性能差距可能超过多数模型优化。

**在调模型之前，先确认目标环境能装什么、装的版本是多少。** 这个检查花五分钟。

## 教训十：诚实地写出"没走完"

FPGA 主线的数值正确性闭环没有完成。可以选择把所有中间产物包装成成功，也可以选择
把失败边界精确到具体环节。

后者更有价值：

- 它告诉后来者**不要重复踩同一个坑**
- 它把问题范围从"整个项目"缩小到"stitched-IP 集成"
- 它让其余所有成果更可信 —— 因为读者知道这个作者不会粉饰
