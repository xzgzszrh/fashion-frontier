# BNN-PYNQ 二值网络路线

## 路线定位

BNN-PYNQ 是 FINN 工具链早期验证的经典 1W1A（1-bit 权重 + 1-bit 激活）全连接网络
（LFC）。

本项目**没有机械复活依赖 Python 2.7 的历史仓库**，而是在当前
PyTorch + Brevitas + QONNX + FINN 统一体系内重建了 paper-style LFC 结构，完整实现
从训练到板端的新版闭环。

这个决定省下的时间比想象中多：维护一套 Python 2.7 的并行环境，成本远高于重写一个
LFC。

## 成功的那次

`paper_bnnpynq_lfc_fashion_1w1a`：

| 指标 | 值 |
|---|---|
| 测试精度 | **83.16%** |
| 最佳验证精度 | 83.87% |
| FINN build | QONNX 导出 → estimate → codegen → ipgen → stitched → full build **全部通过** |
| 板端吞吐（batch=256） | **~154 096 img/s** |
| 板端 bundle 验证 | 256 样本中 214 正确 = **83.59%** |

主机测试精度 83.16% 与板端 bundle 83.59% 高度一致 —— 这一致性本身就是链路健康的
证据。对比 FINN 主线（[05](./05-fpga-finn-deployment.md)）那种"主机 93% / 板端 5%"
的落差，就知道这个一致性有多值钱。

## 失败的那次

首次尝试 `fpga_quant_student_bnnpynq_lfc_w1a1_kdkl_t2_noncheat` 得到**近随机精度
（~10%）**。

失败原因在于**同时叠加了过多高风险变量**：

- 二值 LFC 结构（极低精度模型初始学习极不稳定）
- KL 蒸馏损失（对二值模型 gradient 信号造成干扰）
- cross-entropy 训练语义与标准 sign 激活的兼容性问题

三个变量一起改，崩了以后不知道是谁的锅。这是典型的**变量控制失误**，不是技术能力
问题。

> **教训：对于 1W1A 极端量化模型，应优先稳定纯净训练过程，再逐步引入蒸馏。**

事后看，正确顺序应该是：先跑通无蒸馏的纯净训练（得到 83%），**确认基线成立**，再
单独加蒸馏看是涨还是跌。这样即使蒸馏有害，也只是一次可归因的失败。

## 意义

BNN-PYNQ 路线证明了：在当前 PYNQ-Z1 + FINN 环境下，二值全连接网络 FPGA 部署链路
**完全可行**，并能实现比 CPU-only 路线高出约两个数量级的吞吐：

```
154 096 img/s  vs  445 img/s    ≈ 350×
```

对需要极高吞吐批处理推理的场景（如实时采集流水线）有重要价值。

## 局限

当前主要瓶颈不是部署可行性，而是**模型精度**：

| 路线 | 精度 | 差 |
|---|---:|---|
| CPU-only (INT8) | 92.21% | — |
| BNN (1W1A) | 83.16% | **−9.05** |

1W1A 量化带来约 9–11 个百分点的精度损失，来自两个层面：

1. 1W1A 量化本身的固有精度代价
2. Fashion-MNIST 类间相似性较高（尤其 Shirt / T-shirt / Pullover / Coat 四类），
   对模型表征能力要求高

**在应用精度要求 >90% 的场景下，BNN 路线当前并不适合作为主要交付路线。**

另外要注意：BNN 的混淆集中在 Shirt（类别 6）与 T-shirt、Pullover 之间。如果业务中
这几类的误分类代价高，83% 这个平均数会严重低估实际风险 —— **一定要看混淆矩阵，
不要只看 top-1。**

## 复现

```bash
pip install -e ".[quant]"
frontier train --config configs/quant/bnn_lfc_w1a1.yaml
```

注意配置里**刻意关闭了蒸馏**。想加蒸馏请先跑通纯净基线。
